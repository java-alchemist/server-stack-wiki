# Stack Conventions

Shared patterns enforced across all tva container stacks. Every new stack must follow these.

## 1. One Repo Per App (Fleet Convention)

Each service gets its own git repo, its own system user, and its own Tailscale node identity. No multi-app stacks like the deprecated `media-stack`.

**Rationale:** Blast radius isolation. A container escape from Jellyfin lands on the unprivileged `jellyfin` user, not your admin account or another service's runtime state. Rootless Podman already isolates in a user namespace — stacking a dedicated system user on top of that is defense in depth.

## 2. Repository Structure

```
<stack>-stack/
├── Makefile              # Standard targets (see below)
├── README.md             # Architecture, services table, secrets layout, ops commands
├── podman-compose.yml    # Services definition (podman only — no Docker)
├── .env                  # Local env vars (gitignored; generated by setup.sh)
├── .env.example          # Template with comments (committed)
├── setup.sh              # Provisioning script (bootstrap + local-setup subcommands)
├── serve-config/         # Tailscale SERVE JSON configs
│   └── serve.json        # Routes for this stack's tailscale sidecar
├── secrets/              # 700 dir, 600 files, owned by stack user (gitignored)
│   ├── .tailscale-authkey
│   ├── .dozzle-cert.pem
│   ├── .dozzle-key.pem
│   └── ...               # Stack-specific secrets (e.g. .db_password)
├── shared-deps           # List of files this stack reads from /opt/data/stack-env/
├── ts_state/             # Tailscale node state (bind mount, survives container restarts)
│   └── state.soc         # Node identity — DO NOT delete or the node gets a new hostname
└── [app-specific dirs]   # Config bind mounts, data volumes, scripts/
```

## 3. System User Model

Every stack runs as its **own dedicated system user** (e.g., `jellyfin`, `immich`, `dns`, `dozzle`):

| Concern | Who | Why |
|---------|-----|-----|
| Container runtime | `<stack>` user (nologin) | Rootless podman isolates in a user namespace; an escape lands on the unprivileged service account |
| Repo management | Operator (`bfrey`) + stack user, both in group `server-stack` | You can `git pull` and edit files without sudo |
| Autostart | systemd unit (`User=<stack>`) | Survives reboots, no manual `make up` needed |

The operator account is added to a shared `server-stack` group for repo-level read/write access. The stack user owns runtime state (secrets, ts_state, podman named volumes).

## 4. Secrets Management

**All credentials are files under `secrets/` — never environment variables in `.env`.**

```
secrets/                          # mode 700, owned by <stack>:<stack>
├── .tailscale-authkey            # Tailscale machine auth key (reusable)
├── .dozzle-cert.pem              # Shared mTLS cert (from /opt/data/stack-env/)
├── .dozzle-key.pem               # Shared mTLS key (from /opt/data/stack-env/)
└── .<custom>_password             # Stack-specific secrets
```

Stacks use `*_FILE` compose directives to pass secrets as files into containers:
```yaml
environment:
  POSTGRES_PASSWORD_FILE: /run/secrets/db_password
```

### Shared Secrets (`/opt/data/stack-env/`)

A shared directory at `/opt/data/stack-env/` holds credentials generated once and referenced by multiple stacks:

| File | Generated By | Used By |
|------|-------------|---------|
| `.tailscale-authkey` | dns-stack bootstrap (or operator) | Every stack's tailscale sidecar |
| `.dozzle-cert.pem` / `.dozzle-key.pem` | dozzle-stack bootstrap | Every stack's dozzle-agent (mTLS credential) |
| `common.env` | Created by first stack setup | Sourced by every Makefile (`ENV_LAYER`) |

Each stack declares its shared dependencies in a `shared-deps` file (one relative path per line). `setup.sh` copies these into the stack's `secrets/` and registers them in `$STACK_ENV_DIR/.stack-manifest`.

## 5. Networking

- **No host ports published.** All external access is via Tailscale SERVE reverse proxy.
- Each app gets its **own Tailscale node identity** (userspace networking sidecar container). This gives it a unique `<app>.ts.net` hostname and HTTPS cert domain, which is what lets each serve on standard port 443.
- A single tailscale node can only hold one ts.net hostname/cert — so one app = one node = one SERVE config.
- Podman bridge network (e.g., `jellyfin-net`, `immich-net`) for inter-container communication within the stack.

### Tailscale Sidecar Container

Every stack includes a tailscale sidecar:
```yaml
tailscale:
  image: tailscale/tailscale:v1.102.5   # pinned version
  container_name: <stack>-tailscale
  environment:
    TS_AUTH_KEY_FILE: /run/secrets/tailscale_authkey
    TS_HOSTNAME: <app>                   # e.g., jellyfin, immich
    TS_STATE_FILENAME: state.soc
    TS_SERVE_CONFIG: /etc/tailscale/serve.json
  volumes:
    - ./ts_state:/var/lib/tailscale       # persistent node identity
    - ./secrets/.tailscale-authkey:/run/secrets/tailscale_authkey:ro
    - ./serve-config/serve.json:/etc/tailscale/serve.json:ro
```

### SERVE Config

`serve-config/serve.json` routes HTTPS and raw TCP through the tailscale sidecar:
```json
{
  "443": { "httpsHandle": "app" },
  "7007": { "tcpHandle": "dozzle-agent" }
}
```

Port `:443` → app container (HTTPS). Port `:7007` → dozzle-agent (mTLS gRPC for log collection).

## 6. Dozzle Integration

Every stack runs a `dozzle-agent` service that reports its containers to the central hub (`dozzle-stack`) over mTLS gRPC on port 7007.

```yaml
dozzle-agent:
  image: amir20/dozzle:latest
  container_name: <stack>-dozzle-agent
  command: agent --addr :7007 --cert /run/secrets/cert.pem --key /run/secrets/key.pem
  environment:
    PODMAN_HOST: unix:///run/user/1001/podman/podman.sock   # stack user's rootless socket
  volumes:
    - ${PODMAN_SOCKET}:/run/user/${PUID}/podman/podman.sock  # bind to agent container
    - ./secrets/.dozzle-cert.pem:/run/secrets/cert.pem:ro
    - ./secrets/.dozzle-key.pem:/run/secrets/key.pem:ro
```

On setup, the stack registers its agent endpoint in `$STACK_ENV_DIR/dozzle-agents.d/<stack>` (format: `address|name`). The hub reads all files from this directory on every `make up`.

## 7. Makefile Targets

Every stack's Makefile provides these standard targets. Lifecycle targets self-escalate to the stack user via a passwordless sudoers rule installed by `setup.sh`.

| Target | Description |
|--------|-------------|
| `setup` | Operator entry — host bootstrap (one sudo) then per-stack config |
| `local-setup` | Per-stack files/dirs/secrets only (runs as stack user; re-converge after git pull) |
| `up` | Start the stack (pulls images if missing; self-heals secrets first) |
| `down` | Stop and remove containers/network (named volumes preserved) |
| `restart` | Restart all services in place |
| `upgrade` | Pull latest images, recreate containers (state volumes preserved) |
| `serve` | Re-apply tailscale serve config (restart sidecar; containerboot re-applies serve.json) |
| `status` | Container status table |
| `logs` | Tail logs (`SERVICE=`/`TAIL=` in `.env` for a subset) |
| `validate` | Dry-run compose config with env layering |
| `teardown` | Full removal (containers/volumes/state/secrets/user/group/sudoers) |
| `local-teardown` | Stack-user phase only (containers, volumes, state, secrets) |
| `help` | List all targets with descriptions |

### Makefile Variables

- `STACK` — short name prefix for container names (e.g., `jellyfin`)
- `COMPOSE` — compose file path (default: `podman-compose.yml`)
- `STACK_USER` — system user that runs the containers

### ENV_LAYER

Shared env sourced FIRST, local `.env` second (local wins):
```makefile
ENV_LAYER = set -a; [ -f "$${STACK_ENV_DIR:-/opt/data/stack-env}/common.env" ] && . "$${STACK_ENV_DIR:-/opt/data/stack-env}/common.env" || true; [ -f ./.env ] && . ./.env || true; set +a;
```

## 8. setup.sh Subcommands

The setup script is called by Makefile targets and supports these subcommands:

| Subcommand | Called By | Runs As | What It Does |
|------------|-----------|---------|--------------|
| `setup` | `make setup` | operator → root (bootstrap) → stack user (local-setup) | Full provisioning flow |
| `bootstrap` | internal | root | Create system user, group, linger, subuid/subgid ranges, sudoers rule, server-stack group membership, ownership |
| `local-setup` | `make local-setup` | stack user | Generate `.env`, copy shared secrets from `$STACK_ENV_DIR/`, create directories, register dozzle agent |
| `teardown` | `make teardown` | stack user → root | Remove containers/volumes first, then host-level cleanup (user/group/sudoers) |
| `local-teardown` | `make local-teardown` | stack user | Stack-user phase only (containers, volumes, state, secrets) |

### Bootstrap Checklist (root phase)

1. Create system user (`<stack>`) with home dir and `/bin/bash` shell
2. Ensure subuid/subgid ranges assigned
3. Enable linger (`loginctl enable-linger <stack>`) so rootless podman survives logout
4. Add operator to `server-stack` group; add stack user to `server-stack` group
5. Install passwordless sudoers rule: `/etc/sudoers.d/<stack>-ops` allowing operator to run Makefile targets as `<stack>` without a password
6. Set ownership of repo, secrets dir, ts_state dir to `<stack>:<stack>` (repo files group-writable via `server-stack`)

### Local Setup Checklist (stack user phase)

1. Generate `.env` from `.env.example`, filling in random passwords/secrets
2. Copy shared secrets from `$STACK_ENV_DIR/` into `secrets/` (read `shared-deps` to know which ones)
3. Create runtime directories (`ts_state/`, app config bind mount dirs, etc.)
4. Register dozzle agent endpoint: write to `$STACK_ENV_DIR/dozzle-agents.d/<stack>` with format `<node>.tail6a7569.ts.net:7007|<name>`
5. Enable user-level `podman.socket` systemd unit (so the API socket stays alive for dozzle-agent)

## 9. PUID/GUID in Rootless Mode

**PUID and GUID stay at 0.** In rootless mode, container uid 0 maps to the host user running podman (the stack's system account). Do NOT set `PUID=1000` — it breaks bind-mount ownership because the container writes files as a UID that doesn't exist on the host.

## 10. Data Placement

- **Databases** → named Podman volumes on local disk (heavy fsync + file-locking; network shares handle this poorly)
- **Media/photos** → bind mounts to external storage (e.g., `/mnt/samba_storage/`) where data logically lives with other files
- **App config** → bind mounts in the repo (`./<app>/config/`) so `make migrate` can seed it before first start and changes are version-controlled
- **Tailscale state** → bind mount to `./ts_state/` (node identity survives container recreation)

## 11. Git / GitHub Workflow for Agents

Stack repos live on GitHub (`java-alchemist/<stack>-stack`). The workflow is:

1. **Agent works locally:** Clone/pull the repo, make changes in the working tree
2. **Commit and push to GitHub:** `git add -A && git commit -m "<message>" && git push`
3. **Pull on the target server:** SSH to the host and run `cd /opt/data/.../<stack>-stack && git pull`, then `make local-setup` if generated files need converging, then `make up` or `make upgrade`

This keeps a clean audit trail (commits visible on GitHub) and lets operators review changes in PRs before pulling them to the server. Never commit secrets — they are generated by `setup.sh` and live in gitignored `secrets/`.
