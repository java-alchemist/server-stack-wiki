# dns-stack

Pi-hole DNS resolver + Caddy HTTPS reverse proxy (certs from the home CA via ACME). Own Tailscale node **`dns`**.

## Role in the Fleet

The DNS stack provides two core infrastructure services:

1. **Pi-hole** — Local DNS resolver with ad/tracker blocking and custom `.home.arpa` records for hostname resolution on the LAN/tailnet.
2. **Caddy** — HTTPS reverse proxy for `.home.arpa` hostnames; routes to app backends over their tailnet SERVE endpoints. Certs are issued by the home CA (ca-stack / step-ca) via per-site ACME issuers. Publishes host ports `443:443` and `80:80` directly (setup persists `net.ipv4.ip_unprivileged_port_start=53`).

## TLS / Home CA

Caddy serves `.home.arpa` sites over HTTPS with certs issued from the home CA (ca-stack / step-ca) via ACME. Two non-obvious requirements:

1. **Per-site issuer is mandatory.** certmagic classifies `*.home.arpa` as an *internal* name, and Caddy's Caddyfile adapter assigns its own self-signed local CA to internal names whenever a site has no explicit issuer — the global `acme_ca` option never applies to these sites (caddyserver.com/docs/automatic-https → "Hostname requirements"). Every `.home.arpa` site therefore carries an explicit block:
   ```caddyfile
   tls {
       ca https://home.arpa:9000/acme/caddy/directory
   }
   ```
2. **Trust the ACME channel.** step-ca serves ACME over HTTPS with a self-signed cert (SAN=`home.arpa`, chains to the home root). Caddy trusts it via global `acme_ca_root /etc/caddy/pki/root.crt`; local-setup fetches that file from ca-stack's install page (`http://<tva-lan-ip>:9080/root.crt`) into gitignored `./pki/` (directory-mounted so caddy boots even before the first fetch succeeds — it retries ACME until the root appears).

**Caddyfile syntax traps** (each one crash-loops dns-caddy ~250ms per start, often with no error line in podman logs):
- `tls { ca <url> }` on one line → `Unexpected next token after '{' on same line`. Block contents must start on the next line.
- There is NO per-site `tls off` (single arg must be `internal`, `force_automate`, or an email) and no `protocol http` directive. HTTP-only sites use a `host:80` site key (e.g., the cert install page route).

**Prerequisite for issuance:** FTL hosts records (`FTLCONF_dns_hosts`) must resolve both `<name>.home.arpa` and apex `home.arpa` to tva's LAN IP — step-ca resolves them to reach Caddy. On Pi-hole v6 these live in `[dns] hosts`, NOT the legacy dnsmasq.d mount (inert after the one-time migration).

## SERVE Config

Routes Pi-hole admin UI via Tailscale HTTPS. Caddy serves the `.home.arpa` app routes directly on host ports 443/80 (LAN + step-ca ACME validation) — those don't go through SERVE; each app's own ts.net URL still works in parallel.

```json
{
  "TCP": {
    "443": { "HTTPS": true },
    "7007": { "TCPForward": "dns-dozzle-agent:7007" }
  },
  "Web": {
    "${TS_CERT_DOMAIN}:443": {
      "Handlers": {
        "/": { "Proxy": "http://pihole:80" }
      }
    }
  }
}
```

- `https://dns.<tailnet>.ts.net/admin/` → Pi-hole admin UI (via Tailscale SERVE)
- The handler MUST be `/`, not just `/admin/`: the web UI lives under `/admin/` but its API is at root-level `/api/*` — a `/admin/-only` proxy loads the login page, then every `POST /api/auth` 404s and the UI shows "Server unreachable!"
- Port :7007 → dozzle-agent (raw TCP for mTLS gRPC log collection)

## Pi-hole v6 Notes

- Upstream DNS uses v6 FTL config via `FTLCONF_dns_upstreams` (semicolon-delimited list). Old JSON-bracket form crashes FTL startup (`bad port at line 33`).
- Local records live in FTL `[dns] hosts` (`FTLCONF_dns_hosts`, HOSTS form, semicolon array) — the legacy `/etc/dnsmasq.d/` bind mount is gone; v6 only reads it during the one-time migration.
- Password is read natively via `WEBPASSWORD_FILE=pihole_password` (the file path inside the container).

## Operations

Standard Makefile targets apply (`make setup`, `up`, `down`, `restart`, `upgrade`, `serve`, `status`, `logs`, `validate`, `teardown`). `make rotate-pw` generates a new random web password (same format as setup), writes it to `secrets/.pihole_password`, restarts only `dns-pihole`, and prints the new value once.

### Re-apply SERVE routes

```bash
make serve   # restarts tailscale sidecar; re-applies serve.json for :7007 → dozzle-agent + admin UI proxy
```

## Gotchas

- Pi-hole DNS healthcheck uses `dig +short +norecurse @127.0.0.1 pi.hole` — if this fails, FTL isn't running or the named volume is stale from a v5 migration.
- Low host ports ARE published here (443/80): setup persists `net.ipv4.ip_unprivileged_port_start=53`. Don't "fix" this back to high ports — LAN clients and step-ca's ACME validation expect port-less URLs.
- No host port for DNS on the tailnet — FTL binds :53 directly in the host netns (host networking); Tailscale MagicDNS routes node-IP queries to the right machine.
- **Network backend:** tva's podman build REJECTS pasta (slirp4netns only) — setup.sh actively removes a stray `network_backend = "pasta"` from the dns user's containers.conf. DNS no longer depends on published UDP at all: FTL binds :53 directly via host networking.
- `.home.arpa` sites need the explicit per-site `tls { ca ... }` issuer — global ACME options are ignored for internal names by certmagic. Don't "simplify" this away.

## LAN DNS Access

FTL runs with **host networking** and binds standard port 53 directly in the host netns — no forwarder, no loopback publish. Host-side dnsmasq must stay stopped (`_bootstrap` handles it) or it steals :53.

**Unifi configuration:** In Unifi Controller → Settings → Networks → [LAN] → DHCP Server:
- **DNS 1:** `192.168.1.82` (tva / Pi-hole — primary)
- **DNS 2:** `1.1.1.1` (Cloudflare — fallback if Pi-hole is down)

**Local records** for `.home.arpa` names live in FTL's `[dns] hosts` via `FTLCONF_dns_hosts` in `.env` (HOSTS form, semicolon array): app names + apex `home.arpa` → tva LAN IP (Caddy serves them; step-ca resolves them for ACME), and app ts.net FQDNs → their Tailscale node IPs (Caddy's backends). `make local-setup` rebuilds this from live tailnet state.

## Admin UI Access

Primary admin access is via Tailscale SERVE; a direct web port also exists as an escape hatch:

- **Tailnet:** `https://dns.<tailnet>.ts.net/admin/` (via Tailscale SERVE)
- **Direct (LAN/host):** `http://<tva-lan-ip>:${PIHOLE_WEB_PORT:-10053}/admin/` — the web server binds all interfaces in the host netns; use this when the tailnet is unavailable

App services DO get `.home.arpa` HTTPS routes via Caddy — the earlier objection that "a private CA would need trusting on every device" is solved by ca-stack's install page (`https://ca.<tailnet>.ts.net/`), which enrolls devices into the home CA trust store. The admin UI itself stays off `.home.arpa` (not in the CA allowlist).
