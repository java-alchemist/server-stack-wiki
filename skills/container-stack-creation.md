## When to Use
Create a new container stack repo, add services to an existing one, modify compose/setup/Makefile, or update the wiki docs after any stack change.

## Source of Truth
Read the wiki first for current conventions:
- `/opt/data/server-stack-wiki/conventions.md` — fleet-wide patterns
- `/opt/data/server-stack-wiki/new-stack-guide.md` — step-by-step creation guide
- `/opt/data/server-stack-wiki/stacks/<name>.md` — per-stack docs (dns, dozzle, jellyfin, immich)
Reference implementation: `jellyfin-stack` (`/opt/data/staging/jellyfin-stack/` or GitHub).

## Creating a New Stack

### 1. Scaffold the repo under `/opt/data/staging/<app>-stack/
```
mkdir /opt/data/staging/<app>-stack && cd /opt/data/staging/<app>-stack
git init -b main
```

### 2. Create these files (use new-stack-guide templates)
- `README.md` — architecture, services table, secrets layout, ops commands
- `.env.example` — env var template with comments
- `podman-compose.yml` — app + tailscale + dozzle-agent + watchtower
- `serve-config/serve.json` — Tailscale SERVE routes
- `setup.sh` — provisioning (bootstrap + local-setup subcommands)
- `Makefile` — standard targets (copy from jellyfin-stack, change STACK/STACK_USER vars)
- `shared-deps` — files this stack reads from `/opt/data/stack-env/`

### 3. podman-compose.yml minimum services
1. **App container** — floating tag (`latest`, `release`, `<major>-alpine`). Label with `com.centurylinklabs.watchtower.enable=true`. PUID/GUID = "0" (rootless mode).
2. **Tailscale sidecar** — `tailscale/tailscale:latest` (NOT pinned). Userspace networking + SERVE. No watchtower label.
3. **Dozzle agent** — `amir20/dozzle:latest` with `agent --addr :7007`. Label for watchtower.
4. **Watchtower** — `containrrr/watchtower:latest-ce`, `WATCHTOWER_LABEL_ENABLE=true`, 3600s poll, rolling restart + cleanup.

**Image strategy:** Floating tags for stateless services (watchtower manages). Digest-pin only for databases that can't roll back schema migrations. See immich-stack for the pattern.

### 4. setup.sh subcommands
- `setup` — runs `_bootstrap` (root) then calls `local-setup`
- `_bootstrap` (root) — create system user/group, linger, subuid/subgid ranges, sudoers rule, server-stack group membership, ownership
- `local-setup` (stack user) — generate `.env`, copy shared secrets from `$STACK_ENV_DIR/`, create dirs, register dozzle agent endpoint in `$STACK_ENV_DIR/dozzle-agents.d/<app>`
- `teardown` / `local-teardown` — cleanup

### 5. Makefile
Copy from jellyfin-stack. Change:
```makefile
STACK          := <app>
COMPOSE        ?= podman-compose.yml
STACK_USER     := <app>
```
Customize the `serve` target for your container names.

Standard targets: setup, local-setup, up, down, restart, upgrade, serve, status, logs, validate, teardown, local-teardown, help.

### 6. Secrets management
- All credentials are **files** under `secrets/` (mode 700 dir, 600 files) — never env vars in `.env`
- Use `*_FILE` compose directives to pass secrets as file mounts into containers
- Shared secrets from `/opt/data/stack-env/`: `.tailscale-authkey`, `.dozzle-cert.pem`, `.dozzle-key.pem`
- Stack-specific secrets generated by `setup.sh local-setup` (e.g., random passwords via `openssl rand -hex 32`) → written to `secrets/.<name>` or `.env`

### 7. Push and deploy
``bash
git add -A && git commit -m "initial: <app> stack skeleton"
gh repo create java-alchemist/<app>-stack --private
git push -u origin main
```
Then on the target host:
```bash
cd /opt/data/.../<app>-stack   # clone or move from staging
make setup    # one sudo for bootstrap
make up       # starts everything
make serve    # re-apply SERVE routes
```

### 8. Verify post-setup checklist
- [ ] `loginctl show-user <app> -p Linger` → Linger=yes
- [ ] Operator can edit repo files without sudo (group `server-stack`)
- [ ] `.env` and `secrets/` are gitignored
- [ ] `ts_state/state.soc` exists after first tailscale auth
- [ ] Dozzle agent registered in `$STACK_ENV_DIR/dozzle-agents.d/<app>`
- [ ] SERVE routes work: HTTPS on :443, dozzle-agent on :7007
- [ ] `make validate` passes
- [ ] README.md services table matches actual containers

## Modifying an Existing Stack
1. Edit files in the repo working tree (locally or on the host)
2. Run `make validate`
3. `git add -A && git commit -m "<message>" && git push`
4. On target server: `cd /opt/data/.../<app>-stack && git pull` then `make local-setup`, `make upgrade`, `make serve` (if networking changed)

## Wiki Update Rule
**Always update the wiki in parallel with any stack change:**
- Per-stack docs under `/opt/data/server-stack-wiki/stacks/<app>-stack.md`
- Conventions (`conventions.md`) if fleet-wide patterns change
- New-stack-guide (`new-stack-guide.md`) if templates diverge from reality
Then `cd /opt/data/server-stack-wiki && git add -A && git commit -m "..." && git push`

## Pitfalls
- **PUID/GUID must be 0** in rootless mode. Container uid 0 = host stack user. Setting PUID=1000 breaks bind-mount ownership.
- **No host ports published.** All access via Tailscale SERVE only.
- **One app = one Tailscale node identity.** A single tailscale node can only hold one ts.net hostname/cert.
- **Never commit secrets** — they are generated by `setup.sh` and live in gitignored `secrets/`. If you need a new secret, add the generation step to `setup.sh local-setup`.
- **Databases on local disk.** Never bind-mount DB data to network shares (CIFS unreliable for fsync/file-locking).
- **Tailscale state** (`ts_state/state.soc`) is node identity — DO NOT delete or the node gets a new hostname.
- **Watchtower labels:** Only label app and agent containers. Never label tailscale sidecars or digest-pinned databases.
